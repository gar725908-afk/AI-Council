# NEXUS Mesh — архитектура, транспорты, планы

Что уже работает и как этим пользоваться — в [README](NEXUS_MESH_README_RU.md).
Здесь — устройство модуля и обоснование решений.

## Модули

Новые (`app/src/main/java/ai/hybrid/commandcenter/`):

| Файл | Ответственность |
|---|---|
| `mesh/MeshIdentity.kt` | Ключ устройства в Android Keystore, отпечаток, ID `NX-…`, `SingleKeyManager` для TLS; программный ключ только для тестов |
| `mesh/MeshProtocol.kt` | Кадры, закрытая схема сообщений, операции `MeshOp`, приглашение, HMAC-доказательство, SAS |
| `mesh/MeshTrust.kt` | Реестр доверенных устройств, журнал безопасности, история задач |
| `mesh/MeshGovernor.kt` | Профили ресурсов, проверка до принятия задачи, запрет облачного ядра по умолчанию |
| `mesh/MeshNode.kt` | Узел: TLS-сервер и клиент, сопряжение, сессии, heartbeat, задачи |
| `mesh/MeshRuntime.kt` | Единственный узел приложения, исполнитель на ядре ИИ телефона, mDNS |
| `mesh/MeshService.kt` | Фоновая служба `specialUse` с уведомлением и кнопкой «Остановить» |
| `MeshCenterScreen.kt` | Экран Mesh: узел, Governor, сопряжение (QR/ссылка), устройства, задачи, журнал |

## Схема

```
 Телефон A (координатор сейчас)                Телефон B (исполнитель сейчас)
 ┌───────────────────────────┐                 ┌───────────────────────────┐
 │ Mesh Center (UI)          │                 │ Mesh Center (UI)          │
 │   │                       │                 │                           │
 │ MeshNode ── клиент ───────┼── TCP 47811 ───►│ MeshNode ── сервер        │
 │   │   TLS 1.3, оба ключа  │  mTLS, кадры    │   │   Governor ─ отказ?   │
 │   │   закреплены          │  JSON v1        │   ▼                       │
 │ Trust / история / журнал  │◄── результат ───┤ AppMeshWorker             │
 └───────────────────────────┘                 │   ▼                       │
                                               │ ядро ИИ B: модель на B,   │
                                               │ Ollama на ПК в сети B,    │
                                               │ облако (если разрешено)   │
                                               └───────────────────────────┘
```

Роли не закреплены: у каждого узла есть и сервер, и клиент. После
сопряжения любой из двух телефонов может давать задачи другому.

## Транспорты

| Транспорт | Когда | За | Против | Статус |
|---|---|---|---|---|
| TCP + TLS в локальной сети | один Wi-Fi/LAN | Нет внешней инфраструктуры, минимальная задержка, стандартный TLS платформы | Не работает между сетями; mDNS режется изоляцией клиентов | Implemented |
| Tailscale (WireGuard) | разные сети | Готовый зашифрованный оверлей с обходом NAT, постоянные адреса 100.x; NEXUS ничего не меняет в коде — это частный адрес | Нужны приложение и аккаунт Tailscale; на Android одновременно активен только один VPN | Experimental |
| WebRTC DataChannel | разные сети без стороннего VPN | ICE/STUN/TURN — стандарт обхода NAT | Нужен сервер сигнализации и свой TURN для строгих NAT; большая нативная библиотека | Planned (Phase 3) |
| libp2p | сеть многих узлов | Готовые relay, DHT, multiplexing | Для 2–5 своих телефонов избыточно; зрелость JVM-реализации требует оценки | Оценка (Phase 7), только при доказанной пользе |
| Bluetooth / Wi-Fi Direct | без сети | Работает без роутера | Низкая скорость (BT) / нестабильность групп (Wi-Fi Direct) | Не планируется сейчас |

Документация транспортов: [Tailscale](https://tailscale.com/docs/),
[libp2p](https://libp2p.io/docs/), WebRTC — спецификации W3C/IETF.

Внутри любого транспорта остаётся тот же mTLS NEXUS Mesh: доверие к ключам
устройства не делегируется VPN или серверу сигнализации.

## Подходы к распределённым вычислениям

| Подход | Суть | Когда полезно | Статус |
|---|---|---|---|
| Независимые задачи | Каждая задача целиком на одном узле | Параллельные запросы, несколько агентов Council | Ручная отправка — Implemented; автоматический выбор узла — Phase 4 |
| Реплики | Одна и та же модель на нескольких телефонах, запросы распределяются | Пропускная способность | Phase 4 |
| Разделение модели (llama.cpp RPC) | Слои/тензоры модели на разных устройствах | Модель не помещается в ОЗУ одного телефона | Phase 6 |

Честная оценка разделения модели: трафик между слоями идёт по Wi-Fi, поэтому
для моделей, которые помещаются в один телефон, разделение будет **медленнее**
локального запуска. Смысл — только когда модель иначе не запустить. Это
должен подтвердить замер, а не обещание.

## Resource Governor

`MeshPolicy.evaluate(op, promptChars, DeviceState)` вызывается **до**
`task_accept`. Порядок проверок: профиль выключен → занятость → только на
зарядке → только Wi-Fi → порог заряда (если не заряжается) → нагрев
(`PowerManager` thermal status) → длина запроса. Первый сработавший запрет
уходит отправителю как `task_reject{code=denied}` с причиной по-русски.
Внутри исполнения действуют лимит ответа (генерация прерывается) и тайм-аут
240 с на ответ ядра. Процент CPU обычному приложению Android ограничить не
даёт — поэтому лимиты выражены в задачах, заряде и объёме.

## Планировщик (Phase 4, не реализован)

- Реестр возможностей — из `node.status` (ядро, модель, ОЗУ, заряд, нагрев,
  профиль) и измеренного RTT.
- Выбор узла: подходящая модель → профиль разрешает → наименьшая очередь →
  лучший замер `runtime.benchmark`.
- Повтор на другом узле при `failed`/обрыве; при `denied` — сразу другой узел.
- Контрольные точки для длинных миссий Council: результат каждого агента
  сохраняется в журнал миссии до перехода к следующему.
- Проверка результата: для LLM-ответов — только целостность и происхождение
  (какой узел, какое ядро), «правильность» не утверждается.

## Council на нескольких телефонах (Phase 5, не реализован)

Агенты Council уже работают через `ModelGateway`. План — `MeshGateway`,
который выполняет `inference.run` на выбранном узле, с теми же лимитами и
журналом миссии. Экран Council будет показывать, какой телефон отвечал за
какого агента, — только по факту выполнения.

## Распределение одной модели

Phase 6, не реализован. Ограничения из закреплённых исходников llama.cpp
(`tools/rpc/README.md` в коммите `b1b770d90d94cad9e9ea5b993bdbc383a522fb28`):
RPC-бэкенд — proof of concept, «fragile and insecure», сервер нельзя
запускать в открытой сети. Отсюда требования к реализации:

1. `ggml-rpc-server` на исполнителе слушает только `127.0.0.1`.
2. Координатор достигает его только через туннель внутри аутентифицированной
   сессии Mesh (новый тип сообщений протокола v2), после явного разрешения
   владельца на исполнителе, на время одной сессии.
3. Совместимость: одинаковая версия ggml на всех узлах (сверка в `node.status`),
   иначе — отказ с понятной ошибкой.
4. Сравнение с локальным запуском на той же модели — обязательная часть
   приёмки.

## Совместимость версий

Версия протокола в каждом сообщении (`v=1`). Несовпадение — отказ и разрыв,
задача не запускается. Изменения формата — только с новой версией.
