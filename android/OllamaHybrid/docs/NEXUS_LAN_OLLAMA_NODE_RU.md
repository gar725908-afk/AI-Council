# NEXUS — Ollama LAN Node (Android ↔ PC)

Статус: целевая архитектура интеграции + спецификация следующего runtime slice.
Ветка: `nexus/genesis-foundation`.
Scope: Android NEXUS и отдельный Ollama endpoint на компьютере пользователя. Не изменяет desktop AI Consilium.

## 1. Назначение

NEXUS должен поддерживать два независимых варианта локального inference:

1. **ON_DEVICE** — модель выполняется непосредственно на Android.
2. **LAN_PC_OLLAMA** — модель выполняется на компьютере пользователя через Ollama API в одной локальной сети.

LAN PC Ollama — полноценный first-class inference node, а не временный обходной путь и не облачный API. Android остаётся интерфейсом, владельцем миссий, памяти, политик и разрешений; компьютер предоставляет вычислительный ресурс и выполняет inference.

В типичном домашнем сценарии телефон и ПК подключены к одному Wi-Fi/LAN. NEXUS обращается к адресу ПК и порту Ollama (обычно 11434), получает поток токенов/ответ и отображает его в Android UI. Запросы не должны отправляться в интернет, если выбран именно LAN node и endpoint действительно локальный.

## 2. Схема

```text
┌──────────────────────────────────┐
│ Android: NEXUS                   │
│                                  │
│ NEXUS CORE / Mission Journal     │
│ LocalFirstCouncilOrchestrator    │
│ InferenceRouter                  │
│ OllamaLanEngine                  │
└────────────────┬─────────────────┘
                 │ Wi-Fi / Ethernet LAN
                 │ HTTP(S), streaming
                 ▼
┌──────────────────────────────────┐
│ User PC                          │
│                                  │
│ Ollama server :11434             │
│  ├─ model A (e.g. Qwen)           │
│  ├─ model B (another local model) │
│  └─ model registry/list           │
│                                  │
│ CPU / GPU / RAM of PC             │
└──────────────────────────────────┘
```

Это не требует купленного VPS, публичного IP или проброса порта на роутере. Для связи внутри одной LAN достаточно доступного адреса ПК и разрешённого входящего соединения в локальном firewall.

## 3. Протокол и API

Предпочтительный native Ollama API:
- `GET /api/tags` — обнаружить установленные модели;
- `POST /api/chat` — chat messages, выбранная модель, параметры и stream;
- `POST /api/generate` — completion, если нужен отдельный сценарий;
- `GET /` или тестовый запрос health-check — не считать его достаточным доказательством готовности модели.

OpenAI-compatible endpoint `/v1/chat/completions` может поддерживаться как fallback для совместимых серверов, но для Ollama предпочтителен native API: он даёт более точную семантику списка моделей и параметров.

Требования к Android adapter:
- streaming JSONL из `/api/chat`, корректная обработка последнего неполного буфера;
- отмена HTTP-вызова при отмене coroutine/миссии;
- connect/read/write timeouts и ограничение ответа;
- сериализация истории сообщений без утечки данных в логи;
- поддержка system/user/assistant/tool messages в пределах фактической совместимости модели;
- модель выбирается из фактического ответа `/api/tags`, а не из выдуманного списка;
- отдельная диагностика: unreachable, timeout, model missing, server error, unsupported feature.

## 4. Роль в NEXUS

Добавить транспорт/тип узла `LAN_PC_OLLAMA` и runtime adapter `OllamaLanEngine`, реализующий общий контракт `NexusInferenceEngine`.

Маршрутизация:
- `ON_DEVICE`: приватная локальная модель на Android;
- `LAN_PC_OLLAMA`: модель на сопряжённом компьютере через LAN;
- `WEB_AI_SESSION`: отдельная пользовательская сессия WebView;
- `OPTIONAL_API`: внешний API только после явного включения.

Local Manager может исполняться на ПК через Ollama, но execution location должна быть честно указана как `NETWORK_ENDPOINT` / `LAN_PC`, а не `ON_DEVICE`. Для режима, который требует именно on-device manager, LAN Ollama не подходит. Для обычного LOCAL/HYBRID manager режима это допустимый и предпочтительный мощный локальный узел.

Ожидаемый сценарий:
1. Пользователь задаёт задачу в NEXUS.
2. InferenceRouter выбирает PC Ollama node по политике, доступности, latency и состоянию устройства.
3. NEXUS передаёт контекст выбранной модели на ПК.
4. Ollama исполняет модель на CPU/GPU компьютера.
5. Поток ответа возвращается в Android.
6. LocalFirstCouncilOrchestrator может использовать результат Manager для делегирования участникам Council.
7. Если ПК недоступен, NEXUS предлагает переключить задачу на on-device модель или assisted/manual режим. Автоматическая отправка в облако запрещена без отдельного разрешения.

## 5. Подключение и безопасность

Для первой версии — ручное добавление узла:
- пользователь вводит LAN IP/hostname и порт;
- NEXUS проверяет доступность и получает список моделей;
- пользователь выбирает модель по ID;
- приложение показывает адрес, статус, модель и execution location.

Далее — безопасное pairing:
- одноразовый pairing code/QR, подтверждаемый на обоих устройствах;
- выдача отдельного токена доступа для NEXUS, если PC-side gateway его поддерживает;
- предпочтительно TLS с проверкой сертификата/публичного ключа;
- разрешать соединение только в частной сети и только с сопряжённым узлом;
- никаких автоматических пробросов портов, UPnP или публичного bind;
- не включать Ollama endpoint в публичный интернет.

Важно: стандартный локальный Ollama endpoint обычно не требует API key и сам по себе не предоставляет полноценную аутентификацию для доверенного многопользовательского доступа. Прямой HTTP-доступ к порту 11434 внутри LAN следует считать доверенным plaintext-доступом. Для production pairing лучше использовать отдельный небольшой PC-side authenticated gateway/reverse proxy с TLS, токеном, allowlist и журналом. Не выдавать этот gateway за уже существующую функцию Ollama.

Не хранить в Android логах полный prompt, приватные документы, ответы и секреты. Адрес, порт, выбранная модель и время последнего подключения — метаданные; токены pairing — в Android Keystore.

## 6. Поведение при отказах и автономность

- ПК выключен/спит: узел OFFLINE, миссия остаётся восстанавливаемой.
- Телефон перешёл на мобильную сеть: не обращаться к частному LAN endpoint через интернет и не пытаться обходить сеть.
- Модель не загружена/не найдена: показать список доступных моделей и предложить пользователю запустить/скачать модель на ПК; ничего не скачивать без подтверждения.
- Перегрузка ПК: очередь, timeout, отмена; не запускать параллельно несколько тяжёлых моделей без явного лимита.
- Потеря сети в середине потока: сохранить частичный результат как partial, не маркировать как завершённый.
- Fallback: только по политике пользователя — on-device, assisted/manual или другой заранее разрешённый участник. Никакого скрытого cloud fallback.

## 7. Наблюдаемость и управление

Для каждого узла отображать:
- имя устройства, адрес LAN, порт;
- состояние: paired / reachable / offline / error;
- серверную версию (если доступна);
- список моделей и активную модель;
- время ответа и фактическую execution location;
- статус TLS/authentication;
- кнопку «Проверить соединение» и «Обновить список моделей».

В настройках NEXUS добавить режимы:
- **Только телефон** — inference исключительно ON_DEVICE;
- **Домашний компьютер** — предпочитать LAN_PC_OLLAMA;
- **Гибридный** — выбирать между телефоном и ПК по доступности/нагрузке;
- **Вручную** — пользователь выбирает узел для каждой задачи.

## 8. Этапы реализации

### LAN-0 — существующая основа
- В AI Studio уже имеется OpenAI-compatible gateway и Ollama provider profile.
- Это позволяет вручную настроить совместимый endpoint, но ещё не является полноценным PC node manager, pairing или безопасным обнаружением.

### LAN-1 — OllamaLanEngine
- native Ollama API client;
- streaming parser и cancellation;
- `/api/tags` model discovery;
- endpoint validation и диагностика;
- unit tests на JSONL chunks, malformed events, cancellation, missing model и errors.

### LAN-2 — Node Registry и UI
- несколько сохранённых узлов;
- ручное добавление PC endpoint;
- health checks и выбор модели;
- профили маршрутизации и статус в AI Studio/NEXUS CORE.

### LAN-3 — Secure Pairing
- PC-side authenticated gateway;
- pairing QR/code;
- TLS, token lifecycle, allowlist;
- аудит и ограничение доступа.

### LAN-4 — Council integration
- Ollama node как Local Manager runtime на ПК;
- отдельное отображение `LAN_PC` / `NETWORK_ENDPOINT`;
- безопасный выбор fallback;
- передача контекста через существующие policy/approval gates.

## 9. Критерии готовности

Интеграция не считается production-ready, пока не проверены:
- реальный Android телефон ↔ реальный PC Ollama в одной LAN;
- список моделей соответствует `/api/tags`;
- streaming отображается без потери/дублирования токенов;
- отмена на Android останавливает HTTP stream;
- offline/reconnect и смена Wi-Fi обрабатываются корректно;
- нет скрытого cloud fallback;
- LAN endpoint не доступен извне и не публикуется роутером;
- приватные prompts и ответы не попадают в логи;
- тесты и Android build проходят в CI.

## 10. Границы

Этот механизм не означает, что:
- Ollama уже установлена/настроена на каждом ПК;
- NEXUS сам знает установленную модель до вызова `/api/tags`;
- модель на ПК является on-device моделью телефона;
- Ollama API по умолчанию защищён TLS или API-ключом;
- PC Ollama автоматически даёт NEXUS право выполнять команды на компьютере.

Inference endpoint и Desktop Link — разные функции. Ollama предоставляет генерацию текста/мультимодальных ответов в пределах модели; управление Windows, браузером, файлами или Playwright требует отдельного защищённого Desktop Link с pairing, scopes и approval gates.
