# Исследование 7 — дорожная карта

Порядок — от того, что даёт владельцу пользу сразу, к тому, что требует
больших изменений. Каждый шаг заканчивается проверкой: unit-тесты, сквозной
сценарий на эмуляторе в CI и — где это возможно только на железе — пункт в
чек-листе для телефона владельца. Оценки в «срезах» (один срез — одна
проверяемая порция работы с зелёным CI, как в журнале матрицы реализации).

## Шаг 0 — приёмка на телефоне владельца (блокирует всё «Verified»)

- Установить debug-APK последнего зелёного прогона.
- Чек-лист: подключение ядра (ПК / телефон / облако), ответ модели на
  телефоне (Qwen3.5 0.8B и Gemma 4 E2B), найденный файл GGUF, голос, темы,
  питомец, NEXUS Mesh между двумя телефонами (сценарии 1–3 плана Mesh).
- В Model Center записать строку «Движок GGUF: llama.cpp · CPU: …» — какая
  CPU-сборка выбрана на телефоне.
- **Критерий:** каждый пункт — «работает / не работает + снимок».

## Шаг 1 — скорость локальных моделей (1–2 среза)

Зависит от: шага 0 (нужна строка CPU-сборки и время ответа на телефоне).

- Бенчмарк в Model Center: обработка запроса (pp) и генерация (tg) на
  фиксированном тексте, история замеров — по образцу AiPaca / PocketPal.
- Число потоков по большим ядрам (сейчас `ядра − 1`, от 2 до 6) — менять
  только по результатам бенчмарка.
- **Критерий:** замеры на телефоне владельца до и после, без «оценок на глаз».

## Шаг 2 — GPU для GGUF (2–3 среза)

Зависит от: шага 1 (нужен бенчмарк для сравнения).

- OpenCL-бэкенд llama.cpp для Adreno 7xx/8xx; автоматический откат на CPU,
  если GPU не стартовал; выбор «CPU / GPU / авто» в настройках модели.
- Проверить, какие квантования из каталога поддерживаются OpenCL (по
  документации — Q4_0, Q4_K, Q6_K, Q8_0 и др.).
- **Критерий:** ответ модели на GPU на телефоне с Adreno, замер против CPU;
  на телефоне без Adreno — честный откат и сообщение.

## Шаг 3 — офлайн-голос (2 среза)

- whisper.cpp (base/small) для распознавания; Piper ru_RU для синтеза.
- Выбор «системный / офлайн» в настройках голоса (системный остаётся по
  умолчанию).
- **Критерий:** распознавание и озвучка без интернета на эмуляторе
  (аудиофайл в тесте) и на телефоне.

## Шаг 4 — память и поиск по архиву (2–3 среза)

- Эмбеддинги через llama.cpp (Qwen3-Embedding 0.6B или EmbeddingGemma
  300M), индекс в SQLite, переранжирование bge-reranker-v2-m3 (опция).
- Ответы с цитатами из архива — как сейчас, но поиск по смыслу.
- **Критерий:** тест с набором документов: нужный фрагмент в первых 3
  результатах; работа без сети.

## Шаг 5 — агент на экране (3–4 среза)

- Детекторы залипания, повторов и дрейфа; скриншот, когда дерево a11y
  пустое; передача капчи владельцу.
- Виртуальный дисплей агента через Shizuku: запуск приложения на нём, ввод,
  снимок, закрытие; владелец видит маленькое окно наблюдения.
- **Критерий:** сценарий «открой настройки и включи тёмную тему» на
  эмуляторе на виртуальном дисплее; на телефоне — с Shizuku.

## Шаг 6 — NEXUS Mesh, фазы 3–5 (по плану Mesh)

- Phase 3: проверка через Tailscale на двух телефонах в разных сетях;
  WebRTC — только если Tailscale не подходит владельцу.
- Phase 4: планировщик по профилям узлов (ядро, заряд, RTT, бенчмарк),
  повторы на другом узле.
- Phase 5: агенты совета на нескольких телефонах.
- **Критерий:** гейты из [README Mesh](../NEXUS_MESH_README_RU.md).

## Шаг 7 — MCP-сервер и локальный API (2 среза)

- OpenAI-совместимый API на телефоне (только localhost и сопряжённые
  устройства Mesh, с ключом).
- MCP-сервер NEXUS поверх закрытого канала: инструменты — те же
  типизированные операции Tool Gateway с одобрениями.
- **Критерий:** MCP-клиент на ПК выполняет «состояние телефона» и «ответ
  модели» через сопряжённый канал; без сопряжения — отказ.

## Шаг 8 — по запросу владельца

- Linux-среда (PRoot) — если появится задача, которую иначе не решить.
- Распределение одной модели (llama.cpp RPC) — после планировщика и с
  замером против локального запуска.
- Обновление LiteRT-LM до 0.18+ с проверкой Gemma 4 на эмуляторе.
