# NEXUS Mesh — план тестирования

Три уровня: автоматические тесты на JVM (каждая сборка), сквозной тест на
Android-эмуляторе в GitHub Actions (каждый push в ветку) и ручная проверка
на физических телефонах (делает владелец).

## 1. Автоматические тесты (JVM, Robolectric)

Запуск: `gradle :app:testDebugUnitTest --tests "ai.hybrid.commandcenter.mesh.*"`.
Узлы в тестах — настоящие: TCP-сокеты на `127.0.0.1`, TLS 1.3 через Conscrypt
(BoringSSL), настоящие сообщения протокола. Заглушен только исполнитель
(`EchoWorker` отвечает строкой вместо модели) и Android Keystore (программный
ключ P-256).

| Тест | Что доказывает |
|---|---|
| `twoPhonesPairOverMutualTlsAndRunARealTask` | Сопряжение → оба доверяют друг другу → канал TLS 1.3 → задача выполнена исполнителем, результат вернулся, история у обоих, ping и профиль возможностей |
| `theInviterCallsTheJoinerBackOnItsListeningPort` | Сохраняется настоящий порт присоединившегося (из `hello`), после разрыва пригласивший сам дозванивается и даёт задачу — роли не закреплены |
| `ownerMustConfirmOnBothPhones` | Без подтверждения на обоих телефонах устройство не становится доверенным |
| `wrongSecretAndSwappedKeyAreRefused` | Неверный секрет и подменённый ключ отвергаются |
| `revokedPhoneCanNoLongerRunTasks` | После отзыва задачи не выполняются |
| `resourceGovernorRejectsWithAnHonestReason` | Профиль «Минимум» без зарядки — отказ с причиной, статус «Отклонена» |
| `onlyLocalCoresServeOtherPhonesByDefault` | Облачное ядро для чужих задач запрещено по умолчанию; частные адреса Ollama/LM Studio — локальные, DNS-имена — нет |
| `taskHistorySurvivesARestartAndUnfinishedTasksAreMarkedInterrupted` | История переживает перезапуск, «зависшие» задачи помечаются «Прервано» |
| `storedHistoryIsTrimmedAndRoundTrips` | Хранимая история обрезается и устойчива к испорченным данным |
| `framesRoundTripAndUnknownTypesOrOpsAreRejected` | Закрытая схема: неизвестные типы/операции, лишняя длина — отказ |
| `proofBindsBothKeysAndSasIsSymmetric` | HMAC-доказательство зависит от обоих ключей; SAS одинаков на обеих сторонах |
| `invitesSurviveMessengersAndExpire` | Ссылка переживает переносы строк мессенджеров, истекает через 10 минут |
| `privateAddressRules` | Частные/Tailscale/loopback адреса — да, публичные — нет |
| `governorProfiles` | Пороги профилей |

Скриншот экрана Mesh с настоящим запросом сопряжения между двумя узлами —
`MeshGalleryTest` (`-Pnexus.screenshots=true`, файл `m01_mesh_pairing.png`).

## 2. Сквозной тест: эмулятор ↔ второй узел на машине CI

Workflow `nexus-android-emulator.yml`, скрипт `scripts/emulator-smoke.sh`.

1. Приложение на эмуляторе (Android 14, x86_64) проходит основной сценарий
   и подключает ядро ИИ.
2. Отдельный запуск `NexusSmokeTest#e_meshJourney`: «Модули» → «Mesh» →
   включить узел (ключ создаётся в **настоящем** Android Keystore эмулятора) →
   «Пригласить телефон»; ссылка сохраняется в файл приложения. Снимок 30.
3. На машине CI запускается второй узел (`MeshHostPeerE2E`, программный ключ,
   имя «ПК-узел CI»). Он читает ссылку, закрепляет ключ телефона из неё и
   подключается через `adb forward tcp:47811` — настоящий TCP и TLS до
   приложения на эмуляторе.
4. Телефон показывает код (снимок 31), тест нажимает «Код совпадает»; второй
   узел подтверждает со своей стороны. Снимок 32 — сопряжено.
5. Второй узел: 5 ping, `node.status`, `runtime.benchmark`, затем
   `inference.run` «Ответь одним предложением: что такое NEXUS Mesh?». Ответ
   генерирует ядро ИИ эмулятора. Снимок 33 — задача в истории телефона.
6. Артефакты: `mesh-result.txt` (журнал второго узла с ответом и замерами),
   `mesh-instrument.txt`, `mesh-host.txt`, снимки 30–33, logcat.

Ограничение: второй узел — не Android, а JVM-процесс с тем же кодом узла.
mDNS этим тестом не проверяется (эмулятор за NAT).

## 3. Проверка на физических телефонах (владелец)

Подготовка: свежие сборки NEXUS на всех телефонах, на одном из них
подключено ядро ИИ (модель на телефоне или ПК с Ollama).

| № | Сценарий | Ожидаемый результат |
|---|---|---|
| 1 | Два телефона в одной Wi-Fi: включить узлы, пригласить, отсканировать QR, сверить код, подтвердить на обоих | Оба в «Мои устройства», «На связи · TLSv1.3 …» |
| 2 | С телефона без ядра — «Выполнить там» на телефоне с ядром | Ответ модели второго телефона, задача «Готово» на обоих |
| 3 | В обратную сторону | Тоже работает (роли не закреплены) |
| 4 | Перезапустить Wi-Fi роутер / сменить IP | Телефон находится снова (mDNS), «Подключить» работает |
| 5 | Выключить Wi-Fi на исполнителе во время задачи | Отправитель получает «Сбой», без вечного «Выполняется» |
| 6 | Профиль «Минимум», телефон не на зарядке | Отказ «только на зарядке» |
| 7 | Ядро исполнителя — облако, переключатель облачного ядра выключен | Отказ «Владелец не разрешил…» |
| 8 | «Отозвать» на A | Связь рвётся, задачи от B не принимаются |
| 9 | Отправить ссылку третьему лицу, присоединиться им | На A — запрос с кодом, которого нет на B → «Отклонить» |
| 10 | Закрыть NEXUS свайпом во время задачи, открыть снова | Задача в истории — «Прервано» |
| 11 | Разные сети через Tailscale (оба в одной tailnet) | Сопряжение и задача проходят по адресу 100.x |
| 12 | Три телефона: A даёт задачи B и C по очереди | Обе задачи выполнены, история у каждого |

Сценарии 1–3 закрывают Gate фазы 1–2 из ТЗ («два реальных телефона
доверяют друг другу и обмениваются реальными задачами»).

## Замеры

`runtime.benchmark` возвращает `seconds`, `chars`, `charsPerSecond` для
ответа ядра исполнителя на фиксированный вопрос, плюс время задачи целиком у
отправителя (ядро + сеть). Для сравнения с локальным запуском — тот же вопрос
в чате на исполнителе.

Замеры **на эмуляторе CI** (Android 14 x86_64, 2 ядра, выбран CPU-вариант
llama.cpp с AVX) — это не телефон, цифры только для сравнения сборок:

| Что | Время ответа |
|---|---|
| Qwen3.5 0.8B, найденный файл, сборка llama.cpp `-O0` (до среза 52) | 371.1 с |
| Qwen3.5 0.8B, та же задача, `-O3` + CPU-варианты | 13.4 с (`38e286f`), 17.9 с (`abc1753`) |
| Qwen3 0.6B, скачан из каталога | 17.0 с |
| Gemma 3 270M, найденный файл | 5.9 с |
| `runtime.benchmark` через Mesh (Gemma 3 270M) | 0.82 с, 107 симв./с |
| RTT ping по каналу Mesh (adb forward, одна машина) | 1–2 мс после первого (151 мс) |

На телефонах замеры не проводились.
