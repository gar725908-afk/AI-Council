# NEXUS — Local-first Council и самостоятельное выполнение на Android

Статус: целевая архитектура + первый provider-neutral control-plane scaffold.
Ветка разработки: `nexus/genesis-foundation`.
Область: только Android-проект `android/OllamaHybrid`.
Этот документ не объявляет WebView Council, локальный inference, Desktop Link или Forge production-функциями.

## 1. Принятое направление

NEXUS не должен зависеть от платных API нейросетей или купленного облачного сервера, чтобы выполнять базовые задачи.

Основная схема:

1. **Локальная модель — интеллектуальный Manager.** Она понимает цель, предлагает план, выбирает участников, формирует для них поручения, читает ответы, при необходимости задаёт уточняющие вопросы участникам и формирует итог.
2. **NEXUS CORE — программный runtime и диспетчер.** Он хранит миссию, вызывает Manager, проверяет каждое поручение по политике, направляет его адаптеру, сохраняет результаты, применяет лимиты, отмену и восстановление.
3. **Участники — сменяемые исполнители.** Это может быть другая локальная модель, отдельная пользовательская WebView-сессия бесплатного ИИ, дополнительный API-провайдер или в будущем подключённый компьютер.
4. **Ручной режим остаётся полноценным.** Пользователь может выбрать участника и отправить ему запрос напрямую, не запуская локального Manager.

Таким образом сохраняется механизм оркестрации, но интеллектуальное принятие решений о делегировании переносится к локальной модели. Runtime не удаляется и не отдаёт модели системные полномочия.

## 2. Кто за что отвечает

| Слой | Владелец ответственности |
|---|---|
| Local Manager Model | Анализ цели, выбор стратегии, делегирование, повторные раунды, синтез |
| NEXUS CORE / Orchestrator | Жизненный цикл миссии, планирование исполнения, расписание, лимиты, отмена |
| Policy & Approval | Проверка участника, уровня риска, согласия пользователя и политики передачи данных |
| Participant Adapter | Фактическая доставка поручения и получение результата |
| Verifier | Проверка ответа, полноты и доказательств |
| Mission Journal | История миссии, поручений, ответов и ошибок |

Инвариант: **локальный Manager предлагает действие → NEXUS Policy проверяет → Approval Gate подтверждает, когда нужно → адаптер исполняет → Verifier оценивает → Runtime сохраняет.**

Модель может просить отправить поручение только зарегистрированному включённому участнику. Модель не получает прямого доступа к WebView cookies, произвольным URL, shell, Android API, файлам или системным разрешениям. Ответ участника — недоверенные данные, а не исполняемая команда.

## 3. Режимы Council

### LOCAL_AUTONOMOUS

Локальная модель выбирает участников и запускает разрешённые поручения без подтверждения каждого обычного AI-запроса. Участники, передача контекста которым требует отдельного согласия, всё равно блокируются Approval Gate до подтверждения.

### LOCAL_ASSISTED

Локальная модель предлагает очередной пакет поручений. Пользователь видит список участников и тексты заданий, затем разрешает или отклоняет отправку.

### MANUAL

Пользователь сам выбирает участника и отправляет ему запрос. Локальный Manager не обязателен и не управляет этой отправкой.

Режим можно менять для новой миссии; текущая миссия сохраняет зафиксированную политику, чтобы смена настроек не меняла задним числом разрешения уже выполняемой задачи.

## 4. Классы участников

### 4.1 ON_DEVICE_LOCAL_MODEL

Модель действительно исполняется на телефоне. Она может быть Manager или дополнительным исполнителем. Транспорт отделён от оркестратора.

**Текущее состояние:** в Android runtime пока нет встроенного on-device inference engine. Существующий Ollama профиль подключает уже запущенный endpoint и сам по себе не означает, что модель работает на телефоне. Для настоящего локального исполнения потребуется отдельный Android runtime adapter, загрузка/выгрузка модели и тестирование RAM, нагрева, батареи и производительности.

### 4.2 ANDROID_WEBVIEW_SESSION

Отдельная сессия веб-приложения ИИ внутри NEXUS. Пользователь сам открывает сервис, входит в свою бесплатную/доступную учётную запись и управляет её разрешённой сессией. Разные ИИ получают изолированные профили/хранилища WebView, чтобы не смешивать cookies и аккаунты.

Предусмотреть два способа взаимодействия:
- assisted: NEXUS готовит запрос, показывает его пользователю, пользователь отправляет и подтверждает/передаёт ответ;
- supported automation: автоматизация применяется только к интерфейсам и сценариям, которые технически и правилами сервиса допускаются; используется проверка фактического результата.

Не обходить CAPTCHA, OTP, антибот-защиту, paywall, подписки или ограничения сервиса. Не извлекать cookies из внешнего браузера и не подменять вход пользователя. Веб-интерфейсы могут меняться; каждому адаптеру необходимы version checks, health state и безопасный fallback в assisted/manual режим. Бесплатный тариф не означает безлимитную или гарантированную доступность.

### 4.3 OPTIONAL_API

Дополнительный транспорт, а не фундамент системы. Выключен по умолчанию. Может быть включён пользователем отдельно. Ни одна базовая функция локального Manager не должна требовать API-ключа.

### 4.4 DESKTOP_LINK

Будущий адаптер для существующего desktop AI Consilium. В текущем Android scope он описывается только как контракт/намерение. Он не должен считаться подключённым, пока отдельный настольный проект не будет доработан и согласован по протоколу, безопасности и восстановлению.

Для будущего соединения предпочтительны:
- локальная Wi-Fi/LAN сеть как основной транспорт;
- USB как альтернативный физический транспорт;
- Bluetooth только для обнаружения/сопряжения или малых команд, если тесты подтвердят пригодность.

Облачный сервер не является обязательным. Для связи через разные сети потребуется отдельная защищённая схема, но её реализация откладывается. Нельзя открывать PowerShell, MCP или файловую систему ПК в сеть напрямую.

## 5. Как локальный Manager взаимодействует с другими ИИ

Один цикл:

1. Пользователь отправляет цель.
2. Runtime создаёт/восстанавливает Mission и даёт Manager ограниченный контекст.
3. Manager возвращает структурированное решение `Delegate`, `AskUser`, `Finish` или `YieldControl`.
4. Runtime проверяет IDs участников, состояние сессий, разрешённые транспорты, лимиты размера пакета и необходимость подтверждения.
5. Участники выполняют независимые поручения.
6. Результаты возвращаются в контекст следующего решения Manager.
7. Manager может попросить участника проверить ответ другого ИИ, уточнить противоречие или дополнить решение.
8. Manager формирует итог или просит пользователя вмешаться.
9. Runtime сохраняет события и статус. Недостоверные или неподтверждённые заявления маркируются.

Это не требует, чтобы модели имели общий API или протокол между собой. Общий протокол нужен только внутри NEXUS: контракты поручения, результата и состояния миссии. Каждый внешний интерфейс имеет собственный адаптер.

## 6. Первый добавленный код

Файл:

`app/src/main/java/ai/hybrid/commandcenter/nexus/LocalFirstCouncil.kt`

Добавляет:
- `CouncilControlMode`: LOCAL_AUTONOMOUS / LOCAL_ASSISTED / MANUAL;
- `CouncilParticipantTransport`: ON_DEVICE_LOCAL_MODEL / ANDROID_WEBVIEW_SESSION / OPTIONAL_API / DESKTOP_LINK / MANUAL_EXTERNAL;
- профиль участников и валидацию opt-in для API и Desktop Link;
- типизированные решения локального Manager;
- интерфейсы `LocalCouncilManager` и `CouncilParticipantAdapter`;
- runtime metadata Manager (model ID и ON_DEVICE/NETWORK_ENDPOINT); автоматический режим отклоняет сетевую модель, даже если её назвали локальной;
- явное согласие на передачу контекста внешним WebView/API участникам перед автономной отправкой;
- provider-neutral `LocalFirstCouncilOrchestrator`;
- повторные раунды: результаты участников поступают Manager как контекст следующего решения;
- ограничение параллельности, ограничение количества ходов, защита от неизвестных/выключенных участников;
- отдельный ручной dispatch, работающий без настроенной модели Manager.

Тесты:
`app/src/test/java/ai/hybrid/commandcenter/nexus/LocalFirstCouncilTest.kt`

Покрывают повторные раунды, обязательность локального Manager в автоматических режимах, opt-in API, блокировку отправки без подтверждения и ручную отправку.

**Граница текущей реализации:** интерфейс LocalCouncilManager пока не связан с конкретным on-device inference engine; CouncilParticipantAdapter пока не имеет production WebView реализации; новый control plane ещё не подключён к экрану Council, DI и MissionJournal. Это foundation для интеграции, не заявление о готовом локальном Consilium.

## 7. NEXUS LINK — без обязательного сервера

В будущем Android NEXUS и ПК образуют локальную пару:
- Desktop Agent запускается на компьютере как отдельный процесс/служба;
- телефон находит его в одной LAN;
- пользователь подтверждает одноразовый pairing code на обоих устройствах;
- стороны устанавливают аутентифицированный зашифрованный канал;
- ПК публикует только разрешённые возможности: AI Consilium, Playwright, MCP tools, ограниченная файловая рабочая область и build jobs;
- каждый инструмент имеет отдельные scopes, журнал и approval policy.

PC Agent должен работать по принципу deny-by-default. Запрещено экспонировать произвольный shell/PowerShell, браузерные cookies, полный домашний каталог или MCP без авторизации. Для каждой операции: typed request, allowlist, ограничение времени/вывода и подтверждение для опасных действий. Разработка Android протокола не должна требовать немедленного изменения Desktop Python/PySide6.

## 8. NEXUS FORGE — создание приложений на телефоне

Это отдельный продуктовый модуль, не часть Council транспорта.

Целевая среда:
- Project Workspace с отдельной папкой для каждого проекта;
- редактор кода и дерево файлов;
- Council в роли разработчиков, рецензентов и тестировщиков;
- build adapter с JDK/Gradle/Android SDK или альтернативной совместимой средой;
- APK artifact store, подпись, checksum, лог сборки и установка только после подтверждения пользователя.

До реализации нужно проверить воспроизводимую сборку маленького Android-проекта на реальном целевом телефоне. Наличие редактора/терминала не означает наличие полноценного Android SDK. Не обещать сборку любого проекта: ограничения RAM, диска, ABI и зависимостей должны проверяться. Первую версию можно сделать с проектным редактором и отправкой сборки в доверенную LAN build worker, но это будет дополнительный режим, а не обязательный сервер.

## 10. Критерии готовности

Не считать функцию готовой по факту наличия класса или экрана.

- Local Manager: реальная on-device модель формирует структурированные решения, проходит контракты и работает offline.
- Web Session: пользователь входит в сервис сам; отправка/ответ подтверждаются и восстанавливаются после сбоя; соблюдаются ограничения сервиса.
- Council: Manager реально делегирует, получает результаты и может инициировать второй раунд; история миссии сохраняется.
- Desktop Link: устройство сопряжено, канал зашифрован, доступ к инструментам минимален, опасные команды требуют approval.
- Forge: чистый проект собирается на целевом устройстве или явно выбранной build worker, APK проверяется и устанавливается после подтверждения.

Итог: **локальная модель — интеллект и Manager; NEXUS CORE — диспетчер и гарант исполнения; бесплатные веб-ИИ — сменяемые участники; пользователь — владелец сессий, разрешений и финальных решений.**
