# OllamaHybrid — UI Design System & Screen Specification
Версия документа: 1.0  
Статус: проектная спецификация; не означает, что интерфейс уже реализован в APK.

## 1. Визуальная стратегия

**Направление:** JARVIS BLACK × NEON NEXUS × GHOST PROTOCOL.

- JARVIS BLACK задаёт основу: премиальная тёмная поверхность, дисциплина сетки, ясная типографика, минимум визуального шума.
- NEON NEXUS задаёт энергию: электрический cyan, фиолетовые акценты, тонкие световые контуры, выразительные состояния.
- GHOST PROTOCOL задаёт характер: сетевые карты, потоки событий, технические метки, аккуратные HUD-элементы.

Это не буквальная копия интерфейсов ChatGPT, Claude, DeepSeek, Kimi или экранов из фильмов. Их сильные паттерны изучаются как референсы; графика, компоненты и композиция OllamaHybrid должны быть собственными.

**Главный принцип:** сначала информация и действие, затем эффект. Не превращать каждый блок в светящуюся панель. Неон — средство иерархии, а не постоянная подсветка всего экрана.

### Геометрия и типографика

- Базовая сетка отступов: 4 dp; основные интервалы 8, 12, 16, 20, 24 dp.
- Радиусы: 10 dp для компактных контролов, 14 dp для карточек, 20 dp для крупных панелей, 28 dp для bottom sheets.
- Минимальная интерактивная область: 48 × 48 dp.
- Основной шрифт: системный Roboto / совместимый sans-serif; моноширинный — только для логов, кода, адресов, токенов и телеметрии.
- Заголовки лаконичные; длинные описания не набирать капсом.
- Свечение не должно ухудшать контраст текста. Основной текст — не ниже комфортного контраста WCAG AA.
- Контент не должен упираться в вырезы, статус-бар или системную навигацию.

### Световые эффекты и анимация

- Тонкая подсветка активной границы и короткий переход состояния — стандарт.
- Большие glow-ореолы, scanlines, glitch и частицы — только в отдельных сценах и с низкой интенсивностью.
- Анимация состояния: обычно 140–220 ms; раскрытие крупных панелей 220–300 ms.
- Уважать системную настройку уменьшения анимации.
- Не запускать тяжёлые бесконечные анимации в фоне; экономить батарею и GPU.
- Никаких мерцающих элементов за основным текстом.

## 3. Информационная архитектура

### Главная навигация

Шесть постоянных разделов:

1. **Command Deck** — обзор состояния и быстрые команды.
2. **AI Studio** — диалог с выбранной моделью.
3. **Council** — параллельная работа нескольких агентов и менеджер.
4. **Browser** — самостоятельный браузер и агентная автоматизация.
5. **Models** — локальные и облачные модели, профили и маршрутизация.
6. **Device Core** — мост Android, разрешения, диагностика и ресурсы.

Вторичные разделы из меню или соответствующих экранов: Material Library, Downloads, History, Automations, Tool Center, Permission Center, Diagnostics, Settings.

Навигация должна быть удобна одной рукой. На телефоне — нижняя панель из 5–6 пунктов с компактными подписями; при узкой ширине допускается 5 пунктов и пункт «Ещё». Для планшета и landscape — rail/sidebar. Не дублировать одну и ту же навигацию в нескольких конкурирующих панелях.

## 4. Экраны и их состав

### 4.1 Command Deck — главный экран

**Задача:** за 3–5 секунд понять состояние системы и начать работу.

Состав сверху вниз:

- Верхняя строка: логотип OllamaHybrid, состояние ядра, уведомления, аватар/настройки.
- Карточка текущего профиля: активная модель, источник (Local / Cloud), endpoint, кнопка смены.
- Главная командная строка: поле «Что нужно сделать?» с прикреплением файла, голосом и быстрыми действиями.
- Состояние AI Council: активные агенты, очередь задач, последняя задача, открыть Council.
- Состояние Browser: число вкладок, активная сессия, загрузки, кнопка «Открыть браузер».
- Device Health: батарея, память приложения, доступность bridge, локальный inference endpoint. Не показывать значения, которые приложение реально не измерило.
- Недавние задачи и быстрые сценарии.

**Визуальная иерархия:** одна крупная зона действия, затем компактные карточки статуса. Не делать dashboard из 15 равнозначных карточек.

### 4.2 AI Studio — основной чат

- Верхняя панель: имя модели, Local/Cloud, индикатор соединения, переключатель модели.
- История диалога с чётким разделением сообщений пользователя, модели и инструментов.
- Поддержка Markdown, кода, таблиц, цитат, вложений и копирования.
- Нижний composer: многострочный ввод, attach, voice, send/stop.
- Кнопка инструментов раскрывает доступные инструменты и их разрешения.
- Если модель меняется, диалог и сессия не должны теряться. В заголовке показывать текущий provider/model, а историю хранить независимо от процесса модели.
- Для длинного ответа — индикатор генерации и возможность остановить запрос.
- Ошибки провайдера показывать в контексте: что не удалось, можно ли повторить, сохранён ли текст запроса.

**Важное:** интерфейс не должен имитировать ответ, если модель не ответила. Состояния «отправлено», «генерируется», «инструмент работает», «ожидает подтверждения», «завершено», «ошибка» различаются.

### 4.3 AI Council — командный центр агентов

- Верхняя сводка: Manager Agent, задача, статус выполнения, длительность.
- Список executor-агентов: название, назначение, выбранная модель/provider, состояние, прогресс, последняя активность.
- Визуальная схема связей Manager → исполнители → сводный результат.
- Отдельная лента событий: задача назначена, агент ответил, timeout, retry, конфликт, итог.
- Панель результата с источниками и вкладом каждого агента.
- Контроль: пауза, продолжение, отмена, повтор отдельного агента.
- Настройки параллелизма, таймаутов и стратегии объединения — в настройках задачи, не в постоянном визуальном шуме.

Не изображать «живой» прогресс, если backend не передаёт реальные события. Для неизвестного состояния показывать «ожидание данных».

### 4.4 Browser — полноценный Cyber Browser

Браузер — отдельная рабочая среда, а не WebView, спрятанный внутри чата.

**Основная компоновка:**
- Верхняя зона вкладок с горизонтальной прокруткой, кнопкой новой вкладки и счётчиком.
- Адресная строка: URL / поиск, замок HTTPS, перезагрузка, избранное, меню.
- Область страницы — максимально широкая, без навязчивого HUD поверх контента.
- Нижняя/боковая панель AI Agent: спросить о странице, найти данные, заполнить форму, перейти по ссылке, выполнить сценарий.
- Индикатор режима управления: Human / AI Assist / Agent Running / Waiting for User.
- Журнал действий агента с понятными событиями и кнопкой отмены там, где она реально поддерживается.

**Функции браузера:**
- вкладки и восстановление сессии;
- история, закладки, коллекции;
- загрузки с очередью и управлением файлами;
- JavaScript и DOM в пределах возможностей выбранного движка;
- поиск по странице, выделение, копирование;
- формы, ввод и навигация;
- масштабирование и режим чтения;
- сохранение состояния вкладок после переключения модели или перезапуска приложения;
- передача управления человеку и возврат агенту;
- журнал действий и источник каждого действия.

**Архитектура:** единый WebAccess API и единый BrowserSessionStore для всех моделей. Выбор модели меняет только исполнителя reasoning/tool-call, а не движок браузера, cookies, вкладки, загрузки или историю. Browser engine должен быть изолированным модулем с адаптером; WebView/GeckoView выбираются после проверки требований и лицензий.

**Безопасность и подтверждения:**
- Обычные публичные HTTP/HTTPS сайты доступны без внутреннего списка разрешённых доменов.
- Частные IP, localhost, локальная сеть и системные URI — отдельная зона риска; доступ к ним закрыт по умолчанию и требует отдельного явного разрешения.
- CAPTCHA, OTP, авторизация и антибот-проверки передаются человеку; не обходить защиту сайта.
- Перед оплатой, публикацией, отправкой сообщения, удалением, оформлением заказа и другими необратимыми действиями — экран подтверждения с точным описанием операции.
- Содержимое страниц может отправляться облачному провайдеру, если используется cloud model; это должно быть прозрачно и управляемо.
- Секреты, пароли и cookies не выводить в логи и не передавать моделям без необходимости.
- Доступ агента к странице — через ограниченный набор инструментов, а не произвольный shell.

### 4.5 Models — Model Lab

- Секции Local Models и Cloud Providers.
- Карточка модели: имя, provider, размер/тип, статус доступности, endpoint, контекстное окно — только если известно.
- Действия: выбрать, проверить соединение, задать как default, настроить профиль.
- Переключение модели не должно сбрасывать общий чат, BrowserSessionStore, Council transcript или библиотеку материалов.
- Отдельно показывать «модель доступна», «провайдер подключён» и «генерация работает» — это разные проверки.
- Секреты API хранить в защищённом хранилище Android; не отображать целиком.

### 4.6 Device Core — Android Bridge

- Профиль привилегий: Standard, Shizuku ADB, Shizuku Root, Direct Root.
- Матрица возможностей с источником: Native, App Adapter, Shizuku, Root, Accessibility, Vision.
- Каждая возможность имеет состояния: available, unavailable, permission required, degraded.
- Журнал запросов инструментов: кто инициировал, что запрошено, какой транспорт выбран, результат.
- Для рискованных действий — понятное подтверждение с описанием последствий.
- Раздел диагностики не должен запускать произвольные shell-команды из текста модели.
- Состояние Root/ Shizuku проверять фактически, не выводить фиктивный статус.

### 4.7 Material Library

- Импорт документов, папок и поддерживаемых типов файлов.
- Поиск, фильтры по формату и дате, просмотр карточки материала.
- Отображать реальные этапы обработки: imported, indexed, unsupported, failed.
- Для каждого материала — источник, размер, дата, индексируемый статус.
- Не обещать OCR/PDF/audio/video, пока эти pipeline не реализованы.

### 4.8 Downloads & History

- Загрузки: имя, размер, прогресс, источник, состояние, открыть/поделиться/удалить.
- История браузера и история AI-задач — логически разделены.
- Фильтры и поиск, очистка с подтверждением.
- Сессии браузера восстанавливаются независимо от истории чата.

### 4.9 Permission Center

- Понятный список разрешений Android и зачем они нужны.
- Разделить системные разрешения, Accessibility, Shizuku и Root.
- У каждого разрешения: статус, причина, кнопка перехода в системные настройки, последствия отказа.
- Никакого скрытого включения и никаких ложных обещаний о выдаче прав.

### 4.10 Settings & Diagnostics

Группы: Appearance, AI Providers, Browser, Council, Tools & Permissions, Storage, Privacy, Performance, Logs, About.

Внешний вид: Command Mode / Immersive Mode, плотность Compact / Comfortable, интенсивность эффектов Low / Standard. Изменение темы не должно менять структуру данных или поведение.

## 5. Система компонентов Compose

Создать единый дизайн-модуль и повторно использовать компоненты:

- `HybridScaffold` — корневой каркас и навигация.
- `NeonTopBar` — заголовок и системные статусы.
- `CoreStatusPill` — компактный статус.
- `ModelSelector` — переключение модели/provider.
- `CommandComposer` — единый ввод команд.
- `GlassPanel` — нейтральная поверхность с тонкой границей.
- `AgentStatusCard` — состояние агента.
- `EventTimeline` — последовательность событий.
- `BrowserTabStrip` — вкладки браузера.
- `BrowserAddressBar` — адресная строка.
- `AgentControlDock` — AI/human handoff.
- `PermissionGateSheet` — подтверждение рискованного действия.
- `EmptyState`, `ErrorState`, `LoadingState` — единые системные состояния.

Компоненты должны иметь preview для светлой/тёмной схемы, compact/comfortable и разных ширин. Не создавать отдельную реализацию одной и той же карточки на каждом экране.

## 6. Поведение, доступность и качество

- Основной сценарий должен работать без анимации и без цветовых подсказок.
- Минимум 48 dp для целей касания.
- Поддержка TalkBack: семантические подписи, порядок фокуса, состояние кнопок.
- Поддержка системного размера шрифта и масштабирования.
- Состояния загрузки, пустого экрана, ошибки, offline и permission denied обязательны.
- Сохранение состояния навигации и черновика ввода при смене экрана.
- Критические операции требуют явного подтверждения.
- Никаких ложных индикаторов прогресса, фиктивной телеметрии и декоративных переключателей без функции.

## 7. Архитектурные требования для UI

UI не должен напрямую управлять HTTP, браузерными cookies, shell или провайдерами моделей. Экран читает StateFlow из ViewModel и отправляет типизированные пользовательские намерения.

Рекомендуемые границы:

- `designsystem/` — tokens, typography, shapes, reusable components.
- `feature/commanddeck/`
- `feature/aistudio/`
- `feature/council/`
- `feature/browser/`
- `feature/models/`
- `feature/devicecore/`
- `feature/library/`
- `feature/settings/`
- `core/navigation/`
- `core/session/`
- `core/webaccess/`
- `core/security/`

Состояния UI — immutable data classes; действия — sealed intents/events. Долгоживущие данные (чат, browser tabs, downloads, bookmarks) принадлежат соответствующим репозиториям, а не composable state.

## 8. Рекомендуемый порядок реализации

### Этап A — Foundation
1. Design tokens, typography, shapes, theme.
2. Navigation shell, Command Deck.
3. Системные состояния, accessibility и previews.
4. UI-тесты основных компонентов.

### Этап B — AI workflow
1. AI Studio и сохранение сессий.
2. Model Selector и provider status.
3. Council dashboard, агентные карточки, timeline.
4. Реальные события backend в UI.

### Этап C — Browser workspace
1. Browser engine adapter.
2. Tabs/session persistence.
3. Address bar, history, bookmarks, downloads.
4. WebAccess tools для Council и моделей.
5. AI/human handoff, confirmation gates, security tests.

### Этап D — Device & Library
1. Device Core и Permission Center.
2. Material Library.
3. Diagnostics, settings, logs.

### Этап E — Polish & release
1. Compact/Comfortable density.
2. Command/Immersive modes.
3. Performance, battery, memory and accessibility checks.
4. Screenshots, UI regression tests, device QA.
5. Только после успешной сборки и проверки — APK в GitHub Releases.

## 9. Критерии приёмки дизайна

- Пользователь может определить активную модель, provider и статус соединения без открытия настроек.
- Смена модели не теряет чат, вкладки, cookies, историю, загрузки и состояние Council.
- Browser занимает центральное место как самостоятельный продуктовый модуль.
- Нельзя перепутать действие человека с действием AI-агента.
- Перед необратимым действием отображается конкретное подтверждение.
- Каждая кнопка либо выполняет действие, либо явно disabled с причиной.
- Нет фиктивных данных и декоративных элементов, выдаваемых за работающие функции.
- Все основные экраны читаемы на узком телефоне и масштабируются на планшет.
- Системные разрешения и риски видны пользователю до выполнения действия.
- UI сохраняет производительность при отключённых эффектах и на устройствах среднего класса.

## 10. Референсы и правила заимствования

Изучать UX-паттерны ChatGPT, Claude, DeepSeek, Kimi, Grok и других AI-интерфейсов: composer, история, переключение моделей, streaming, tool calls, citations, attachments, sidebar. Из sci-fi эстетики использовать общие принципы HUD, тактических панелей, сетевых визуализаций и restrained neon.

Код, графические ресурсы, логотипы, шрифты и скриншоты сторонних проектов не копировать без проверки лицензии и прав. Репозитории с GPL и другими copyleft-лицензиями не переносить в проект автоматически. Предпочитать собственную реализацию по открытым UX-паттернам.

---

**Итог:** OllamaHybrid должен выглядеть как единая AI-операционная среда, а не как набор несвязанных экранов. Cyberpunk-стиль формирует характер; единая архитектура состояния, ясная навигация, безопасность и реальные функции формируют качество продукта.
