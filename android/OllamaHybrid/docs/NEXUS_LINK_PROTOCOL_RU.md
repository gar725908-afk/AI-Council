# NEXUS LINK — спецификация протокола v2

Первый пункт этапа LFC-4. Описывает, что агент на ПК разрешает телефону NEXUS
и как это проверяется. **Без публичного сервера и без облачного аккаунта.**

Android-сторона реализована (`nexus/LinkProtocol.kt`, 15 юнит-тестов
`LinkProtocolTest`). Desktop Agent — отдельная программа, ещё не написана,
см. «Что сделано и что нет» в конце.

## 0. Что изменилось в v2 и почему

Версия 1 сама сопрягала телефон и ПК: шестизначный код на обоих экранах и
`session_key = SHA-256("nexus-link:v1:" + код + nonce_телефона + nonce_ПК +
отпечаток)`. Nonce и отпечаток шли открытым JSON, поэтому у ключа было всего
~20 бит секретности: кто записал обмен и хоть одно сообщение, защищённое
ключом, перебирает все 10⁶ кодов офлайн. Тест `v1 pin handshake falls to an
offline search over all codes` это показывает: в CI-окружении код нашёлся за
доли секунды, полный перебор — около 2,5 с на одном ядре. Это не PAKE и не
честный SAS — замечание технического аудита (приоритет 1) подтверждено.

В v1 не было ни транспорта, ни агента на ПК — уязвимая схема нигде не
работала. Поэтому её не «чинили», а **удалили**: в v2 у LINK нет собственного
сопряжения и собственной криптографии. Тест `the pin handshake is gone from
v2` следит, чтобы функции v1 не вернулись.

## 1. Принципы

1. **Одна сеть.** Агент на ПК — обычное устройство NEXUS Mesh: сопрягается
   так же, как телефон (128-битный секрет приглашения, взаимный TLS с
   закреплёнными ключами, HMAC-доказательство, шестизначный код с
   commit–reveal, подтверждение на обоих экранах). Отдельной «сети LINK» нет;
   LINK — логический канал поверх той же доверенной TLS-сессии, со своими
   правами. См. `NEXUS_MESH_PROTOCOL_RU.md`, раздел «Сопряжение».
2. **Deny-by-default.** Пока агент не выдал именованную возможность, телефон не
   может вызвать на ПК ничего. Произвольный shell/PowerShell, cookies браузера,
   домашний каталог и ключи **не существуют как возможности** — их нельзя
   запросить даже теоретически.
3. **Личность — из канала, а не из сообщения.** Выданные права привязаны к
   закреплённому ключу Mesh той сессии, по которой пришёл ответ. Отпечаток,
   написанный внутри сообщения, игнорируется. На сессии другого устройства
   права ничего не стоят.
4. **Только сужение.** Агент может выдать лишь часть того, что телефон просил.
5. **Опасное — отдельно.** Опасные возможности телефон запрашивает только после
   отдельного подтверждения владельцем каждой из них.
6. **Всё журналируется.** Каждый вызов проходит те же одобрения и аудит, что и
   локальные инструменты Bridge.

## 2. Возможности (scopes)

| id | Что открывает | Опасная |
|---|---|---|
| `council` | AI Consilium на ПК | нет |
| `mcp_tools` | MCP-инструменты ПК | нет |
| `workspace_read` | Чтение рабочей папки проекта | нет |
| `workspace_write` | Запись в рабочую папку проекта | да |
| `build_jobs` | Сборочные задания | да |
| `browser_automation` | Автоматизация браузера (Playwright) | да |

**Запрещённые навсегда:** `shell`, `powershell`, `cmd`, `exec`, `cookies`,
`home`, `filesystem`, `root`, `keychain`, `credentials`, `ssh`. Тест
`forbidden capabilities can never be granted or invoked` следит, чтобы ни одна
из них не появилась в перечислении и не прошла проверку доступа.

## 3. Обмен правами

```
Телефон                                   ПК (Desktop Agent)
   ═══ уже сопряжены через NEXUS Mesh: взаимный TLS, ключи закреплены ═══
   |  {protocol:"nexus-link", version:2,     |
   |   device, scopes:[…]}                   |
   |--------------------------------------->|
   |               владелец ПК выбирает, что разрешить
   |  {protocol:"nexus-link", version:2,     |
   |   agent, scopes:[…]}                    |
   |<---------------------------------------|
   |  Grant = {agent, scopes,                |
   |   agentFingerprint = ключ этой сессии}  |
```

Функции: `requestJson`, `parseGrant(json, sessionFingerprint, now)`,
`acceptGrant(request, grant, meshTrusted)`, `isAllowed(grant,
sessionFingerprint, scopeId)`, `needsConfirmation(scopes)`.

### Условия отказа (все проверяются тестами)

| Условие | Поведение |
|---|---|
| ПК не сопряжён через NEXUS Mesh | Отказ: «сначала сверь код на обоих экранах» |
| У сессии нет закреплённого ключа (не 64 hex) | Отказ |
| ПК не выдал ни одной возможности | Отказ |
| ПК выдал возможности, которых телефон не просил | Отказ |
| Другой протокол или версия (в т. ч. v1) | Ответ не разбирается |
| Запрещённые и неизвестные id | Отбрасываются при разборе |
| Права предъявлены на сессии другого устройства | `isAllowed` = нет |

## 4. Вызовы после выдачи прав

Каждый запрос несёт id возможности. Перед отправкой телефон проверяет
`isAllowed(grant, sessionFingerprint, scope_id)`; отсутствие возможности или
чужая сессия — отказ на стороне телефона, не дожидаясь ответа ПК. Окончательно
права проверяет агент на ПК для каждого входящего вызова. Опасные возможности
дополнительно требуют одноразового подтверждения пользователя через Gateway,
как и привилегированные локальные инструменты.

## 5. Требования к Desktop Agent

- реализовать сопряжение и сессию NEXUS Mesh v2 (без своей криптографии);
- deny-by-default, типизированные запросы, allowlist путей;
- проверять права на каждый вызов по ключу TLS-сессии;
- ограничение времени и объёма вывода на каждую операцию;
- отдельный журнал на стороне ПК;
- подтверждение для опасных действий;
- запрет экспонировать shell, cookies, домашний каталог и MCP без авторизации;
- не требует немедленных изменений в существующем desktop-проекте на Python.

## 6. Что сделано и что нет

**Сделано (Android):** модель возможностей с запрещённым списком, привязка прав
к ключу сессии Mesh, приём прав только от сопряжённого устройства и только в
пределах запроса, проверка доступа deny-by-default, отметка опасных
возможностей, форматы сообщений. Схема v1 с PIN удалена. 15 юнит-тестов,
включая демонстрацию офлайн-перебора v1.

**Не сделано:** операции LINK в протоколе Mesh (появятся вместе с агентом) и
**Desktop Agent для ПК** — отдельная программа, которую нельзя проверить без
реальной пары «телефон + компьютер» в одной сети. ТЗ ставит Desktop Agent
отдельной веткой после согласования с состоянием desktop-проекта.
