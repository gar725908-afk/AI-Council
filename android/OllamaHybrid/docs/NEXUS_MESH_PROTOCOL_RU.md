# NEXUS Mesh — протокол v2

Исходники: `mesh/MeshProtocol.kt` (формат, схема, сопряжение), `mesh/MeshNode.kt`
(поведение узла). Тесты: `MeshProtocolTest`, `MeshNodeTest`.

## Транспорт

- TCP, порт по умолчанию **47811** (`MeshProtocol.DEFAULT_PORT`).
- Поверх TCP — TLS 1.3 (или 1.2 на Android 8–9, где 1.3 нет) с **обязательной
  взаимной аутентификацией** (`needClientAuth = true`).
- Разрешённые наборы: TLS 1.3 (`TLS_AES_*`, `TLS_CHACHA20_*`) или TLS 1.2
  `TLS_ECDHE_ECDSA_WITH_*` только с GCM/ChaCha20 — всегда эфемерный ECDHE и
  AEAD (прямая секретность).
- Сертификат каждой стороны — самоподписанный, ключ EC P-256 из Android
  Keystore. Доверие держится не на цепочке сертификатов, а на **отпечатке
  ключа**: SHA-256 от `SubjectPublicKeyInfo` (64 hex-символа).
- ID устройства для людей: `NX-XXXX-XXXX` — первые 8 hex отпечатка
  (`MeshFingerprint.deviceId`). Узел обязан представиться ID, который
  соответствует его TLS-ключу, иначе соединение рвётся.

## Кадры

```
+----------------+---------------------------+
| длина: int32 BE| JSON-объект, UTF-8        |
+----------------+---------------------------+
```

- Длина 1…262 144 байт (`MAX_FRAME = 256 KiB`); иначе — разрыв.
- Каждое сообщение — JSON-объект с полями `v` (версия, сейчас `2`) и `t` (тип).
- Схема **закрытая**: неизвестный тип, неизвестная операция, строка вместо
  объекта, поле длиннее лимита — `ProtocolException` и разрыв соединения.
  Ничего не десериализуется в произвольные объекты.

## Типы сообщений

| `t` | Поля (лимит длины) | Кто и когда |
|---|---|---|
| `hello` | `device` (32), `name` (40), `app` (24, необяз.), `port` (0…65535, необяз.) | Первым после TLS в обе стороны. `port` — где отправитель слушает (0 — не слушает) |
| `pair_request` | `invite` (32), `proof` (64 hex), `commit` (64 hex) | Присоединяющийся, сразу после `hello`, если ещё не доверен |
| `pair_nonce` | `nonce` (32 hex) | Пригласивший, после верного `proof`: его случайное число |
| `pair_reveal` | `nonce` (32 hex) | Присоединяющийся: раскрывает число, на которое дал `commit` |
| `pair_confirm` | — | Каждая сторона после нажатия «Код совпадает» |
| `pair_reject` | `reason` (300, необяз.) | Отказ сопряжения (неверная ссылка, отказ владельца) |
| `ping` / `pong` | `n` (число) | Heartbeat и замер отклика |
| `status_request` / `status` | `profile` (объект) | Профиль возможностей узла |
| `task` | `id` (40), `op` (40, из списка), `params` (объект) | Запрос задачи |
| `task_accept` | `id` | Исполнитель принял задачу |
| `task_progress` | `id`, `note` (200) | Промежуточный статус |
| `task_result` | `id`, `output` (64 000) | Итог |
| `task_reject` | `id`, `reason` (300), `code` (`denied` / `failed` / `cancelled`) | Отказ Governor'а, ошибка, отмена |
| `task_cancel` | `id` | Отправитель отменяет задачу (в т. ч. по тайм-ауту) |
| `error` | `reason` (300, необяз.) | Фатальная ошибка, соединение закрывается |
| `bye` | `reason` (300, необяз.) | Вежливое закрытие |

Сообщения кроме `hello`, `ping/pong`, `bye` и сообщений сопряжения принимаются
только от **доверенной** стороны; от недоверенной — разрыв.

## Операции (`op`)

Закрытый список `MeshOp`; командной строки и произвольного кода нет.

| `op` | `params` | Результат |
|---|---|---|
| `node.status` | — | JSON-профиль: Android, ABI, ядра, ОЗУ, память, заряд, зарядка, нагрев, доступные движки, текущее ядро ИИ, профиль Governor'а |
| `inference.run` | `prompt` (строка), `system` (необяз., ≤ 2 000) | Ответ ядра ИИ исполнителя (лимиты профиля) |
| `runtime.benchmark` | — | `{"core", "seconds", "chars", "charsPerSecond"}` — реальный ответ на фиксированный вопрос |

Права (`grants`) хранятся у каждого сопряжённого устройства; по умолчанию —
все три операции.

## Приглашение

`nexus-mesh:1:` + base64url(JSON без паддинга):

| Поле | Значение |
|---|---|
| `i` | ID приглашения (9 случайных байт, base64url) |
| `s` | секрет, 16 случайных байт (`SecureRandom`) |
| `f` | отпечаток ключа пригласившего (64 hex) — закрепляется присоединяющимся |
| `d` | ID устройства пригласившего |
| `n` | имя (≤ 40) |
| `a` | адреса `host:port` (≤ 8, каждый ≤ 64) |
| `e` | срок действия, Unix-секунды; TTL 10 минут |

Тот же текст показывается QR-кодом. При разборе пробелы и переносы строк
(мессенджеры) игнорируются; отпечаток проверяется по формату, секрет — по длине.

## Сопряжение

```
Присоединяющийся (B)                         Пригласивший (A)
  ── TCP + TLS (B закрепил ключ A из ссылки; A принимает любой ключ) ──►
  hello{device=ID(B), port}  ───────────────►  проверка ID(B) ↔ ключ B
                             ◄───────────────  hello{device=ID(A), port}
  проверка ID(A) == d из ссылки
  Nb = 16 случайных байт
  pair_request{invite, commit, proof} ──────►  проверка приглашения и proof;
                                               приглашение занято этим B
                             ◄───────────────  pair_nonce{Na}   (Na = 16 случайных байт)
  pair_reveal{Nb} ──────────────────────────►  проверка commit == H(…Nb)
                 обе стороны показывают SAS и ждут владельца (≤ 2 мин)
  pair_confirm  ◄──────────────────────────►  pair_confirm
                 оба подтверждения → TrustedPeer сохранён, сессия доверенная
```

- `commit = SHA-256("nexus-mesh-commit-v2|" + invite + "|" + fp(A) + "|" + fp(B) + "|" + Nb)`, hex.
- `proof = HMAC-SHA256(secret, "nexus-mesh-pair-v2|" + invite + "|" + fp(A) + "|" + fp(B) + "|" + commit)`,
  hex. `fp` — отпечатки ключей, **реально увиденных в этом TLS-соединении**.
  Посредник, который терминирует TLS своим ключом, меняет `fp` и не может
  вычислить верный `proof`, не зная секрета; а B ещё и отвергнет его ключ, так
  как закрепил `fp(A)` из ссылки. Сравнение — за постоянное время.
- `SAS = SHA-256("nexus-mesh-sas-v2|" + fp(A) + "|" + fp(B) + "|" + invite + "|" + Na + "|" + Nb)`,
  первые 4 байта как число mod 10⁶, вид `123 456`. Роли фиксированы: A —
  пригласивший, B — присоединяющийся.
- **Почему commit–reveal.** B обязуется своим `Nb` до того, как увидит `Na`, а
  `Na` появляется только после этого. Код не существует, пока не раскрыты оба
  числа, и ни одна сторона не может подогнать своё число под чужое. Так
  устроено числовое сравнение в Bluetooth Secure Connections и хеш-обязательство
  в ZRTP. В v1 код зависел только от двух ключей и приглашения: тот, у кого
  утекла ссылка и кто видел код на экране B, мог перебирать сертификаты, пока
  один не даст те же 6 цифр (~10⁶ попыток, секунды на одном ядре —
  `MeshProtocolTest.v1CodesCouldBeSteeredByTryingKeysV2CodesCannot`). В v2 у
  такого человека одна слепая попытка из миллиона, и каждая неудача видна
  владельцу как несовпадение кодов.
- **Одно сопряжение на приглашение.** Как только `proof` верен, приглашение
  занято этим B; второе устройство с той же ссылкой (фото QR) получает отказ
  «Приглашение уже использует другое устройство» и не может перехватить
  идущее сопряжение. После сопряжения или сбоя приглашение не действует —
  нужно создать новое. 3 неверных `proof` уничтожают приглашение; без
  приглашения недоверенный узел может только получить отказ. Не больше 10
  недоверенных подключений в минуту.
- Раскрытие, не совпавшее с обязательством, — отказ «Проверка кода
  сопряжения не прошла», код не показывается, событие в журнале безопасности.
- Тайм-ауты: соединение 5 с, рукопожатие и сообщения до показа кода 20 с,
  ожидание подтверждения владельцем 120 с.

## Доверенная сессия

- Переподключение: исходящая сторона пробует адреса устройства (найденный
  через mDNS — первым, затем сохранённые), закрепляя его отпечаток.
- Входящая сторона узнаёт адрес для обратного вызова из поля `port` в `hello`
  (адрес источника + объявленный порт), а не по эфемерному порту источника.
- Исходящая сторона шлёт `ping` раз в 15 с и `status_request` после
  установления; нет ответа на ping за 10 с — сессия закрывается. Сокет
  закрывается после 50 с тишины.
- Новое соединение с тем же устройством заменяет старое (старое закрывается).

## Жизненный цикл задачи

```
отправитель: SENT ──task──► исполнитель: Governor
                               ├─ отказ ─► task_reject{denied} ─► REJECTED
                               └─ task_accept ─► ACCEPTED ─► RUNNING (task_progress)
                                     ├─ task_result ─► DONE
                                     ├─ ошибка ─► task_reject{failed} ─► FAILED
                                     └─ task_cancel ─► task_reject{cancelled} ─► CANCELLED
тайм-аут у отправителя → task_cancel, FAILED «Нет ответа за N с»
```

История — 60 последних задач на каждом телефоне, хранится в приватных
настройках приложения: ID, операция, статус, короткая заметка (≤ 300), ответ
обрезан до 2 000 символов. При старте незавершённые задачи помечаются
`FAILED` «Прервано: приложение было закрыто».

## Обнаружение в локальной сети

DNS-SD через `NsdManager`: тип `_nexus-mesh._tcp`, имя `NEXUS-<ID>`, TXT —
`id`, `fp` (первые 16 hex отпечатка), `v`. Обнаружение только подсказывает
адрес: доверие всё равно проверяется отпечатком в TLS.

## Совместимость версий

`v` в каждом сообщении. Узел с другой версией получает отказ «Версия
протокола не совпадает» и соединение закрывается — задача не запускается.
v2 (ноябрь 2026) изменил только сопряжение; узлы v1 и v2 не сопрягаются и не
соединяются — на обоих телефонах должна стоять одна версия NEXUS. Формат
ссылки-приглашения (`nexus-mesh:1:`) не менялся.
